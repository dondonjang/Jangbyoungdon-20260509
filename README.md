# 생필품 장바구니 비서

35-50세 여성 소비자의 반복 구매 생필품/식료품 재구매 의사결정 비용을 줄이기 위한 AI 쇼핑 비서 MVP입니다.

사용자가 상품 상세 링크를 입력하면 상품을 구조화하고, `자주 사는 상품` 기준으로 동일 상품 가격 비교와 유사 추천 상품 후보를 확인할 수 있도록 설계했습니다.

## 테스트 URL

- 테스트 배포: https://msa-cyan.vercel.app/
- 현재 테스트 기준 유저는 `id=1`로 고정되어 있습니다.
- 컬리 상품 상세 링크를 입력하면 상품 등록 후 `자주 사는 상품` 화면에서 수집/분석 상태와 추천 결과를 확인할 수 있습니다.

## 기본 테스트 방법

### 로컬 실행

```bash
bun install

```

브라우저에서 `http://localhost:3000` 또는 실행 로그에 표시되는 로컬 주소로 접속합니다.

### 빌드/정적 검증

```bash
bunx tsc --noEmit --pretty false --project tsconfig.json
bun run lint
bun run build
```

현재 shadcn UI 일부 파일에서 React Fast Refresh 관련 경고가 남을 수 있습니다.
과제 기능 동작에는 영향을 주지 않는 경고로 보고, 별도 UI 컴포넌트 정리 작업으로 분리했습니다.

### 크론 수집 확인

Vercel 배포 기준으로 아래 크론이 1분 주기로 등록되어 있습니다.

- `/api/cron/collect-price-comparisons`
- `/api/cron/collect-related-products`

로컬에서는 아래처럼 직접 호출해 수집 흐름을 확인할 수 있습니다.

```bash
curl "http://127.0.0.1:3000/api/cron/collect-price-comparisons?limit=1&timeBudgetMs=30000"
curl "http://127.0.0.1:3000/api/cron/collect-related-products?limit=1&timeBudgetMs=30000"
```

라이브 배포는 Vercel Deployment Protection 설정에 따라 직접 `curl` 호출이 401로 막힐 수 있습니다.
이 경우 Vercel 대시보드의 Cron/Logs 화면이나 `vercel curl`로 확인합니다.

## 핵심 플로우

1. 사용자가 채팅창에 상품 상세 링크를 입력합니다.
2. 서버가 상품 상세 정보를 수집합니다.
3. AI가 상품명, 핵심 속성, 동일 상품/유사 상품 검색 키워드를 구조화합니다.
4. 상품을 `자주 사는 상품`에 저장합니다.
5. 저장 상품 화면에서 동일 상품 후보와 유사 추천 상품 후보를 분리해 보여줍니다.

## 서비스 구조

```text
src/routes/api/
  products/                     # 프론트에서 사용하는 상품 등록/조회 API
  cron/                         # Vercel Cron이 호출하는 후속 수집 API
  scrape/                       # 수집 링크 파싱과 수집 대상 관리 API
  internal/                     # 내부 확인용 API

src/server/db/
  prisma.ts                     # Vercel Node 런타임 기준 Prisma Client 생성
  timestamps.ts                 # KST 기준 timestamp 생성 헬퍼

src/server/services/
  product/                      # 상품 등록, 저장 상품 조회, 후속 수집 오케스트레이션
  scrape/                       # 컬리/다나와 수집기와 링크 파서
  market/                       # 마켓 판별, 마켓별 어댑터, 공통 마켓 클라이언트
  ai/                           # OpenAI 호출과 AI 요청 로그

src/lib/
  product-types.ts              # 프론트/서버가 공유하는 상품 응답 타입
  product-status.ts             # 코드상에서 사용하는 상품 수집 상태 상수
  product-rules.ts              # 동일/추천 상품 판단에 쓰는 공통 규칙
  product-functions.ts          # 클라이언트에서 호출하는 서버 함수 래퍼
```

서비스는 `상품`, `수집`, `마켓`, `AI` 네 가지 책임으로 나눴습니다.
파일을 너무 잘게 쪼개기보다, 과제 리뷰어가 한 번에 따라갈 수 있는 단위로 묶는 것을 우선했습니다.

현재 흐름은 아래처럼 이어집니다.

1. `src/routes/api/products/index.ts`가 사용자 상품 등록 요청을 받습니다.
2. `product-registration-service.ts`가 마켓 판별과 상품 저장을 담당합니다.
3. `kurly-collector.ts`가 컬리 상품 정보를 수집하고, 필요한 경우 OpenAI가 검색 키워드를 보강합니다.
4. `collect-price-comparisons.ts` 크론이 다나와 동일 상품 후보를 수집합니다.
5. `collect-related-products.ts` 크론이 다른 사용자 관심 상품 후보를 수집합니다.
6. `saved-product-view.ts`와 `frontend-product-service.ts`가 프론트 표시용 응답으로 정리합니다.

## 구현 설명 및 설계 의도

### 개발 흐름

이번 구현은 처음부터 완성된 정답을 놓고 달린 작업이라기보다, 상품 링크 하나를 입력했을 때 실제로 어디까지 자동화할 수 있는지 좁혀가며 만든 작업에 가깝습니다.

초기에는 프론트 화면과 백엔드 수집 구조를 분리하는 것부터 시작했습니다.
이후 컬리 PLP/PDP 수집 가능성을 확인하고, 다나와 검색 결과와 카탈로그 페이지를 가격 비교 후보로 연결했습니다.
마지막에는 Vercel 배포, Prisma 기반 DB 연결, 내부 크론, OpenAI 기반 키워드/속성 추출까지 붙여서 과제 데모에서 한 흐름으로 설명 가능한 형태를 목표로 정리했습니다.

커밋 로그 관점에서는 아래 순서로 의사결정이 이어졌습니다.

1. 스크랩 백엔드 1차 구조를 만들고, 실제 상품 데이터를 가져올 수 있는지 확인했습니다.
2. OpenAI는 전면 기능이 아니라 상품명 정제, 속성 추출, 추천 검색어 생성처럼 판단 보조 역할로 제한했습니다.
3. Vercel 배포를 위해 Cloudflare/Wrangler 전제를 제거하고, TanStack Start/Vercel 런타임에 맞게 DB 연결을 정리했습니다.
4. 다나와 가격 비교 링크와 컬리 저장 상품을 분리해, 사용자가 입력한 상품과 외부 가격 비교 후보를 같은 테이블에 섞지 않도록 했습니다.
5. 최종적으로 사용자가 보는 화면에서는 `자주 사는 상품`, `가격 비교`, `다른 사용자 관심 상품`처럼 과제 설명이 쉬운 언어로 정리했습니다.

### 문제 범위 설정

처음에는 AI 쇼핑 비서가 해결할 수 있는 문제가 넓었습니다.
상품 탐색, 가격 비교, 리뷰 요약, 장바구니 최적화, 재구매 알림까지 모두 가능해 보였습니다.

하지만 범위가 넓으면 MVP에서 무엇을 검증하는지 흐려진다고 판단했습니다.
그래서 35-50세 여성 소비자에게 반복적으로 발생하는 장보기 상황에 집중했습니다.
그중에서도 "새 상품 발견"이 아니라 "이미 자주 사는 상품을 다시 살 때의 비교 피로"로 문제를 좁혔습니다.

### 제품 컨셉

단순 최저가 검색은 기존 가격비교 서비스와 차별점이 약합니다.
더 중요한 페인포인트는 가격을 모르는 것이 아니라, 시간이 부족한데도 판단해야 할 기준이 많다는 점이라고 봤습니다.

그래서 제품 컨셉을 `최저가 검색`이 아니라 `자주 사는 상품 기준의 재구매 의사결정 보조`로 정의했습니다.
UI도 일반 검색 결과가 아니라 `자주 사는 상품`을 중심으로 구성했습니다.
동일 상품과 유사 추천 상품을 구분해 보여주는 이유도 이 때문입니다.

### AI 사용 범위

AI를 전면에 내세우기보다, 사용자가 실제로 체감하는 구매 판단 비용을 줄이는 데 사용했습니다.

AI의 역할은 상품명 정제, 속성 추출, 동일 상품/유사 상품 검색 키워드 생성으로 제한했습니다.
사용자가 보는 가치는 "AI가 생각했다"가 아니라 "내가 다시 살 상품과 대체재가 정리되어 있다"는 경험이라고 판단했습니다.

### 구현 범위 선택

처음부터 여러 커머스를 모두 지원하면 수집 안정성, 데이터 정합성, 추천 품질을 동시에 해결해야 합니다.
그래서 초기 MVP는 제한된 상품 링크 입력과 저장 상품 화면에 집중했습니다.

입력 베이스는 상품 PDP 내 정보고시가 비교적 명확하고 수집 난도가 낮은 컬리로 잡았습니다.
가격 비교 후보는 구조적으로 수집 가능한 다나와를 활용했습니다.
제한된 범위 안에서 문제를 끝까지 검증하기 위한 선택입니다.

### 백엔드 설계 의도

백엔드는 화면을 위한 단순 API와, 시간이 걸리는 수집/분석 작업을 분리했습니다.
사용자 상품 등록은 빠르게 응답하고, 가격 비교 상품과 다른 사용자 관심 상품 후보는 크론에서 후속 수집하는 구조입니다.

이렇게 나눈 이유는 외부 페이지 수집과 OpenAI 호출이 항상 빠르고 안정적이라고 볼 수 없기 때문입니다.
사용자에게는 먼저 `수집 중입니다`, `분석 중입니다` 상태를 보여주고, 수집이 끝난 데이터는 다음 조회에서 자연스럽게 붙는 흐름을 의도했습니다.

DB 구조도 당장은 과한 정규화를 피했습니다.
상품 원천 데이터는 `Product`, 외부 가격 비교/추천 후보는 링크/오퍼 구조로 분리하고, 상세 이미지나 정보고시처럼 원본 형태가 중요한 데이터는 JSON으로 보관했습니다.
초기 과제 단계에서는 스키마를 너무 잘게 쪼개기보다, 실제 수집 데이터가 안정적으로 쌓이는 구조를 우선했습니다.

### 프론트 설계 의도

프론트는 검색 서비스처럼 보이기보다, 내가 다시 살 가능성이 높은 상품을 관리하는 도구처럼 보이도록 구성했습니다.
그래서 메인 언어도 `상품 분석`보다 `자주 사는 상품`을 우선했습니다.

동일 상품 카탈로그 자체를 과하게 노출하기보다는, 사용자가 당장 판단할 수 있는 최저가 중심 가격 비교와 다른 사용자 관심 상품을 간결하게 보여주는 방향을 선택했습니다.
추천 후보도 너무 많이 펼치지 않고 일부만 먼저 보여준 뒤 더보기로 확장하는 구조를 의도했습니다.

## 강조하고 싶은 부분

- 문제를 "AI 쇼핑" 전체가 아니라 반복 구매 의사결정 비용으로 좁혔습니다.
- `자주 사는 상품`을 중심에 두어 사용자의 기존 구매 맥락을 저장하는 구조로 설계했습니다.
- 동일 상품과 유사 추천 상품을 분리해, 최저가와 대체재 판단을 섞지 않으려 했습니다.
- 서버 전용 수집/AI 로직과 클라이언트 UI 경계를 분리했습니다.
- Vercel 배포를 고려해 Cloudflare/Wrangler 구조를 다시 도입하지 않았습니다.
- 외부 수집 실패를 예외가 아니라 상태로 보고, 크론에서 다시 채울 수 있는 구조로 설계했습니다.
- OpenAI 결과를 그대로 믿기보다, 액세서리/보관함 같은 명백한 비동일 상품은 규칙 기반 필터와 함께 걸러내도록 했습니다.

## 아쉬웠던 점과 개선 여지

- 현재 MVP는 지원 입력 범위가 좁습니다.
  컬리 상품 상세 링크 중심으로 검증하고, 이후 다른 커머스와 상품명 입력으로 확장하는 방향이 필요합니다.

- 추천 품질을 더 정교하게 검증해야 합니다.
  AI 키워드만으로는 동일 상품과 유사 상품의 경계가 흔들릴 수 있어, 용량, 브랜드, 모델명, 단위 가격 같은 deterministic signal을 함께 써야 합니다.

- 가격 비교는 실시간성보다 신뢰성이 중요합니다.
  이후에는 수집 시점, 배송비, 쿠폰, 품절 여부를 더 명확히 보여줘야 합니다.

- 실제 사용자 테스트가 필요합니다.
  35-50세 여성 10-20명에게 최근 반복 구매 상품을 입력하게 하고, 저장률, 비교 후보 클릭률, 재사용 의향을 확인하는 실험이 다음 단계입니다.

- 로그인/가족 공유는 후순위로 두었습니다.
  핵심 문제 검증 전에는 범위가 커지기 때문에, 먼저 저장 상품 기반의 재구매 행동이 실제로 발생하는지 확인하는 것이 우선이라고 판단했습니다.

- 크론과 수집 상태를 운영 화면에서 더 잘 보여줄 필요가 있습니다.
  현재는 API와 로그 중심으로 확인하는 구조라, 실제 운영 단계에서는 최근 수집 시간, 실패 사유, 재시도 횟수를 관리자 화면에서 확인할 수 있어야 합니다.

- 추천 점수화 로직은 더 고도화할 수 있습니다.
  지금은 과제 데모 기준으로 가격, 리뷰, 평점, 동일 카테고리, 동일 입수 같은 기준을 우선순위화했지만, 실제 서비스에서는 단위 가격, 배송비, 품절, 쿠폰, 사용자 선호 브랜드까지 함께 반영해야 합니다.

- 시간이 부족해 UI를 더 매끄럽게 다듬지 못한 부분이 남아 있습니다.
  핵심 플로우를 먼저 완성하는 데 집중했기 때문에, 로딩 상태, 빈 상태, 추천 후보 펼침/닫힘, 모바일 화면의 세부 인터랙션은 추가 개선 여지가 있습니다.

- 상품 등록 시 이미 확보된 데이터를 더 빠르게 반영할 수 있습니다.
